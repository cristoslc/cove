# Cove Data Inventory & Governance Policy

## Why this exists

`cove` is a stateless CLI, but the operator's state MUST persist across
reinstalls, upgrades, and backup transfers to new machines. The `cove up`
regression that clobbered the Speedtest APP_KEY was a symptom of a deeper
misstep: **state lives in many places with no inventory and no governance**, so
derived artifacts get wiped, sources of truth collide, and there is no rule for
reconciling them.

This document is the **inventory first, then the policy**. The inventory is the
evidence; the policy derives from it.

## Governing principle

A **regenerable derivation** may be synthesized from up to three inputs:

1. **The wheel** — templates, defaults, playbooks shipped in `cove` itself.
2. **The user's pre-existing config** — identity, preferences, machine facts.
3. **The service's current state** — live databases, vault contents, seeded rows.

The CLI is a **reconciler across these three external sources of truth** — it
holds none itself. Where they disagree, precedence must be explicit (see
`docs/adr/` for the precedence rule, once decided).

## State inventory

State is spread across ~7 locations. Each entry classifies: **source of truth**
(wheel / user-config / service-state / external / derived), **durability**
(durable = must survive everything; derived = regenerable), and **backup
coverage** (Documents/ is captured by Time Machine/Syncthing/restic).

| `vault/data/` | Vault Raft storage (secrets, op-cache) | service-state | **yes** | Encrypted at rest |
| `vault/logs/` | Vault audit logs | derived | no | |
| `pages/sites/` | Deployed static sites | service-state | **yes** | |
| `speedtest/` | Speedtest DB (incl. `database.sqlite`) + app data | service-state | **yes** | Admin row seeded here |
| `litellm/pgdata/` | LiteLLM Postgres data | service-state | **yes** | Optional profile |

### 2. `~/.config/cove/` — control-plane (MIXED: partly wiped, partly durable)

| Path | What | SoT | Durability | Reinstall? | Notes |

| `compose/host_vars/` | (empty example only) | — | — | — | Real host_vars live in `state/hosts/` |
| `VERSION` | Install version marker | derived | no | — | |

## What this exposes

1. **The `compose/` tree mixes wheel-content with durable artifacts** (`.env`,
   `certs/`). Because `extract_resources()` rmtree's the whole tree, the durable
   bits get wiped on every reinstall. The CA correctly lives in `pki/` (survives);
   the `.env` and cert copy do not. **The flaw is the mixed tree, not the
   individual files.**

2. **Admin identity has 4 co-existing copies that can diverge:** 1Password
   (canonical) → Vault KV cache → compose `.env` → **service DB row**. We watched
   this collision live with Speedtest. Precedence is undefined.

3. **Backup asymmetry:** the harbor payload (`~/Documents/cove-data/`) is the
   only thing guaranteed backed up. The CA key, keychain, `.env`, and host_vars
   are NOT in Documents/ — a fresh machine restore must re-derive them, and the
   CA key in particular is irreplaceable.

## Open policy questions (feed the ADR)

- Precedence when 1Password / Vault / `.env` / service-DB disagree (probe: DB is
  a **sink**, 1Password is canonical, Vault an offline cache — but confirm).
- Which artifacts must be physically separated out of the rmtree'd `compose/`
  into durable homes (`state/`, `pki/`, Documents/).
- Whether backup must cover the control-plane (CA key, keychain) or whether
  re-derivation + 1Password restore is an acceptable recovery story.
- New-machine bootstrap: what must be copied vs regenerated vs re-pulled.

# Cove Secrets in Keychain, Replacing .env

Cove currently stores all compose secrets in a plaintext `.env` file at `compose/.env`. This file holds the Vault root token, Forgejo admin password, and (with the Dagu addition) MinIO root credentials and ntfy tokens. The file persists on disk indefinitely.

## Current State

`compose/.env` is generated by Ansible on first `cove up` and never deleted. It contains:

```
VAULT_ROOT_TOKEN=...
FORGEJO_ADMIN_PASSWORD=...
MINIO_ROOT_USER=...
MINIO_ROOT_PASSWORD=...
...
```

This file is readable by the user. It's in a gitignored directory. But it persists on disk forever — if the machine is stolen, compromised, or backed up to cloud storage, the secrets are exposed.

## Proposal: Keychain as Source of Truth

macOS login keychain is already unlocked when the user is logged in. Cove already uses it — `cove creds vault-get` retrieves the Vault root token from the keychain. Extend this to all compose secrets.

### Flow

1. `cove creds put <key> <value>` stores a secret in the keychain under a `cove.` service prefix
2. `cove up` reads all needed secrets from the keychain, writes them to `compose/.env`, runs `docker compose up`, then deletes `compose/.env`
3. No plaintext secrets file persists on disk between runs

### Lifecycle

```
cove up
  → read secrets from keychain (login keychain, already unlocked)
  → write compose/.env (chmod 600)
  → docker compose up -d
  → rm compose/.env
  → done (secrets only existed in memory + .env for seconds)
```

On `cove down`, no cleanup needed — `.env` was already deleted after `cove up`.

### What Lives in Keychain

| Secret | Keychain Key | Used By |
|--------|-------------|---------|
| Vault root token | `cove.vault-root-token` | `cove creds vault-get`, bootstrap |
| Forgejo admin password | `cove.forgejo-admin-password` | provisioning |
| MinIO root user | `cove.minio-root-user` | compose env |
| MinIO root password | `cove.minio-root-password` | compose env |
| ntfy tokens (future) | `cove.ntfy-<topic>-token` | compose env |

### What Doesn't Live in Keychain

- Vault-stored secrets (app credentials, API keys) — stay in Vault
- 1Password-sourced secrets — stay in 1Password, synced to Vault via `cove creds`
- Non-secret config (ports, hostnames, image tags) — stays in `compose/.env.example` and `group_vars/all.yml`

## The `.env` Exposure Window

The `.env` file exists on disk only during `cove up` execution — typically seconds. If the machine crashes between write and delete:

- The file persists on disk in plaintext
- On next `cove up`, it's overwritten and then deleted
- The exposure window is from crash to next boot

Mitigations:
- `chmod 600` on `.env` (user-readable only)
- `.env` in a gitignored directory (no accidental commit)
- `cove down` could also delete `.env` as a safety net
- A launchd job could sweep for stale `.env` files on boot

This is strictly better than the current pattern where `.env` persists forever.

## Migration Path

1. **Add keychain storage** — `cove creds put` and `cove creds keychain-get` commands
2. **Migrate existing `.env` secrets to keychain** — one-time migration on `cove up`
3. **Switch `cove up` to keychain-first** — read from keychain, write temp `.env`, delete after compose up
4. **Remove `.env` persistence** — `.env` is ephemeral, not committed to disk

Step 1-2 can happen in one sashay. Step 3-4 in a follow-up once keychain storage is verified.

## Relationship to Dagu

Dagu doesn't block on this. The Dagu sashay uses the existing `.env` pattern — Dagu/MinIO/ntfy secrets are added to `.env` like any other compose secret. The keychain migration is a separate sashay that replaces the `.env` mechanism for all services.

## Open Questions

1. **Linux support?** Linux doesn't have a login keychain. Options: `pass` (GPG-based), `secret-tool` (libsecret), or a file-based fallback with `chmod 600`. Cove is macOS-first, so this is a future concern.
2. **Keychain access from containers?** Containers can't read the keychain. `cove up` reads keychain on the host and passes secrets via `.env`. Containers never touch the keychain.
3. **Multiple machines?** Keychain is per-machine. For multi-machine Cove (tier-2), secrets would need to be provisioned per machine. Same as today — `.env` is per-machine too.
